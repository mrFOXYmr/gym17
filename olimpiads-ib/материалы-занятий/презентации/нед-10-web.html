    Теория. Где живут web-уязвимости

  • Приложение обрабатывает пользовательский ввод (параметры, body, header).
  • Если ввод попадает в файловую систему (LFI), в SQL-запрос (SQLi),

    • в шаблон (SSTI) или в параллельную операцию (Race) — это уязвимость.

  • Главное: понять, куда уходит ввод, и сломать именно ту логику.

    • Тема 10.1. Local File Include (LFI)

    Через параметр читают файлы сервера.

    http://<ip>/...?file=config.js
http://<ip>/...?file=/etc/passwd

    Зачем: раскрыть конфиг/исходник → найти ключ/флаг.

    Разбор образца Innopolis: маршрут /profile в app.js содержит LFI.

    LFI vs RFI

  • LFI — подключаем локальный файл сервера.
  • RFI — удалённое включение (загрузка внешнего файла/скрипта).
  • LFI чаще встречается в олимпиадах; RFI требует включения URL.

  • Прочитать config.js через LFI.
  • Почему важно читать именно config.js (конфиг приложения).

    • Тема 10.2. SQL injection

    Манипуляция параметра, чтобы изменить/обойти запрос.

  • «Вход без пароля»: username=admin&password[password]=1 (НТО «Baby node»).
  • ' or '1'='1' -- — классика.

    • Признаки SQLi: магический логин, аномальные параметры, ошибки БД.

    Как защищает prepared statement

  • Значения передаются отдельно от SQL-кода.
  • Ввод не интерпретируется как часть запроса → инъекция невозможна.
  • «prepare_your_statements_properly» — намёк на параметризацию.

    • ПРАКТИКА Б. Признаки SQLi

  • Распознать SQLi по строке (что здесь «магия»?).
  • Как защищает prepared statement.
  • Придумать простой пример обхода.

    • Таблицы и примеры — из НТО/2022-2023/infbez-отбор-тур2.

    Теория. Механика SQLi

  • Запрос строит строку с подстановкой ввода: WHERE user = '...'.
  • Ввод ' or '1'='1' -- закрывает кавычку и «вешает» вечно-истинное условие.
  • --/# комментирует остаток запроса.
  • Результат: обход логина, чтение таблиц, иногда запись.
  • Защита от этой механики — prepared statement (параметризация).

    • Тема 10.3. Template injection (SSTI) — НТО «X-Forwarded-For»

    X-Forwarded-For: 1, {{ config }}

    → сервер отработал шаблон и вернул флаг NTO{Da_n3_localhost_...}.

    Когда это возможно: пользовательский ввод попадает в шаблонизатор (Jinja2/Flask).

    SSTI vs XSS

  • XSS — код исполняется в браузере жертвы.
  • SSTI — ввод исполняется на СЕРВЕРЕ в шаблонизаторе.
  • Тест SSTI: {{7*7}} → если вернёт 49, есть template injection.

    • Тема 10.4. Race Condition

    Гонка при параллельных запросах (НТО «BLOCKchain»).

  • Одновременные запросы → несогласованное состояние → флаг.
  • Признак: операции зависят от «проверки-и-действия» без синхронизации.
  • Эксплуатация: множество параллельных запросов (Burp Intruder, скрипт).

    • Общий алгоритм решения web-таска

  • Зайти, осмотреть (исходник, JS, /robots.txt).
  • Определить технологию (Flask/Node/Express).
  • Проверить простые уязвимости: LFI, SQLi, комментарии, дефолтные доступы.
  • Искать флаг в ответе.
  • При необходимости — автоматизировать повтор (Python, burp).

    • РАЗБОР ФЛАГА. SSTI через X-Forwarded-For

    Тест: отправить заголовок с шаблоном и проверить отклик.

    curl -H "X-Forwarded-For: 1, {{ 7*7 }}" http://<ip>/
# если в ответе "49" — есть SSTI
    Ответ

    {{7*7}} → 49 подтверждает template injection.

    Дальше: {{ config }} в X-Forwarded-For → видим SECRET_KEY.

    Флаг-формат: NTO{...} — ищем в отрендеренном шаблоне.

    • Типовые ошибки

  • Путают LFI и SSTI.
  • В SQLi забывают про prepared statement (не всегда = инъекция).
  • Не определяют технологию → неверный вектор.
  • В гонках не используют параллельные запросы.

    • Резюме: что уносим

  • Уязвимости живут там, куда уходит пользовательский ввод.
  • LFI, SQLi, SSTI, Race: механика, признаки, примеры.
  • Prepared statement — защита от SQLi.
  • Алгоритм web-таска: осмотр → технология → простые уязвимости → флаг.
